# Skill：周边去哪儿（Nearby Explorer）

## 1. 名称与用途

- **名称**：周边去哪儿（Nearby Explorer）
- **用途**：根据用户给出的位置、地点类型和步行时间限制，查询附近真实地点，逐一带上步行路线信息，返回最多 3 个可直接前往的推荐。
- **适用场景**：
  - “我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。”
  - “我在北京国贸，附近有没有 10 分钟内能走到的公园？”
  - “从这附近找两家步行 20 分钟内能到的餐厅。”
- **不适用**：多站行程规划（本题每个地点都是同一起点的独立备选）、驾车/公交路线、跨城市行程编排。

---

## 2. 输入理解（先解析，再查询）

从用户输入中提取以下字段；缺哪项就按下表兜底，不要凭空假设。

| 字段 | 提取方式 | 缺失时的处理 |
|---|---|---|
| 起点 | 用户给的坐标或地名 | 若只给地名，先用地理编码工具（`maps_geo`）转成坐标；仍无法确定就向用户确认，不要猜 |
| 地点类型 | 关键词（咖啡馆、餐厅、公园…） | 未指定类型时，问清需求或按“值得去的地方”通用搜索并在回答中说明按通用类型处理 |
| 步行时间上限 | “不超过 15 分钟”“10 分钟内”等 | 未指定时，**不设上限但按距离升序取值**，并在回答中说明“未指定时间上限，已按距离由近到远推荐” |
| 数量上限 | “最多 3 家”“两家” | 未指定时默认 3 个，硬性不超过 3 个 |
| 偏好 | “优先近一点”“安静点”“评分高” | 只对**有数据支撑**的偏好排序（距离、时长）；无数据的偏好标注“未核实” |

> 硬约束：**数量 ≤ 3**，且所有推荐必须 **步行时长 ≤ 用户给的上限**。

---

## 3. 执行流程（必须按顺序）

### 步骤 1｜确定起点坐标

- 用户已给坐标（如 `120.15,30.28`）→ 直接使用，保持工具要求的经纬度顺序。
- 用户给的是地名/地铁站/商圈 → 调用地理编码工具（`maps_geo`）取第一个结果的坐标，并把**解析到的标准地名回显**给用户（例如“按‘杭州东站’理解”），避免起错点。

### 步骤 2｜周边地点搜索

- 工具：地点搜索（`maps_around_search`，按关键字 + 中心点 + 半径搜索周边）。
- 参数：
  - `keywords`：用户要的地点类型（如“咖啡馆”）；
  - `location`：步骤 1 得到的坐标；
  - `radius`：**由步行时间上限换算**，按步行速度约 80 米/分钟估算（15 分钟 ≈ 1200 米），在此基础上留 20% 余量取整；用户未给时间上限时取 2000 米。
- 记录返回的每个候选：名称、地址、坐标、类型、距离（若接口返回）、POI ID。

### 步骤 3｜逐个查询步行路线（不可跳过）

- 工具：步行路线规划（`maps_direction_walking`），`origin` = 起点坐标，`destination` = 候选坐标。
- 只对**步骤 2 的候选**逐个调用，取回：步行距离（米）、预计耗时（分钟/秒）。
- **必须使用路线工具返回的距离与耗时**，禁止用直线距离、地图目测或估算值替代。
- 若候选较多（> 10），先按步骤 2 返回的距离粗排，取最近的 10 个再查路线，以控制调用次数；若粗排后仍不足，再补查。

### 步骤 4｜严格筛选

对每个有路线结果的候选执行：

1. 丢弃 **步行耗时 > 时间上限** 的候选（不能“接近就算通过”）；
2. 丢弃类型明显不符的候选（例如要咖啡馆却返回便利店）；
3. 丢弃路线查询失败、返回为空或数据缺失的候选（不要用其它数据补位）。

### 步骤 5｜排序与取前 N

- 用户说“优先近一点”或未指定偏好 → 按**步行耗时升序**（耗时相同按距离升序）。
- 用户明确说“评分高/环境好”等无数据偏好 → 仍按耗时排序，但在回答中说明“该偏好缺少数据支撑，未作为排序依据”。
- 取前 **min(数量上限, 3)** 个。

### 步骤 6｜组织回答

按第 4 节的格式输出，并附一句“数据来源：高德地点搜索 + 步行路线规划”。

---

## 4. 回答格式

必须用表格列出推荐，每行包含：名称、地址、步行距离、步行时间、推荐理由。

```
按「咖啡馆 · 步行 ≤ 15 分钟 · 最多 3 家 · 优先近的」为你找到 3 个（起点：杭州东站）：

| # | 名称 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|------|------|---------|---------|---------|
| 1 | XX 咖啡（XX 店） | 江干区 XX 路 12 号 | 420 米 | 约 6 分钟 | 三家里步行最近，6 分钟可达 |
| 2 | YY Coffee | 江干区 YY 街 8 号 | 780 米 | 约 11 分钟 | 步行 11 分钟，仍在 15 分钟内 |
| 3 | ZZ 咖啡 | 江干区 ZZ 路 30 号 | 1050 米 | 约 14 分钟 | 步行 14 分钟，接近上限 |

数据来源：高德地点搜索（周边 1200 米）+ 步行路线规划。
说明：营业状态与排队情况未核实；如需更近的选择，可把时间上限收到 10 分钟。
```

- 表格后最多补 1–2 句提示（如放宽条件、换类型），不要长篇解释。
- 数字单位统一（米 / 分钟），耗时统一写“约 N 分钟”。
- 不要输出工具原始 JSON，也不要暴露内部思考过程。

---

## 5. 异常与边界处理（必须遵守）

| 情况 | 处理方式 |
|---|---|
| **结果不足**（符合条件的不足请求数量） | 如实说明“在 X 米范围内只找到 N 个满足步行 ≤ Y 分钟的地点”，把已找到的全部列出，并建议放宽时间上限或扩大范围。不因数量少而编造。 |
| **一个都没有** | 明确说明未找到符合条件的结果，给出两条可操作建议（放宽到 N 分钟 / 换用相近类型），不要用不符合条件的候选凑数。 |
| **路线查询失败或返回空** | 该候选不进入推荐；若全部失败，说明“步行路线查询失败，无法确认可达时间”，不输出距离与时长。 |
| **地点搜索失败/超时** | 说明服务暂时不可用，建议稍后重试；不得凭记忆或推测给出地点。 |
| **信息缺失（营业时间、排队、安静程度、评分）** | 一律标注“未核实”，不得编造，也不得作为排序依据。 |
| **用户地点类型模糊** | 先按最接近的类型搜索，并在回答中说明“按 XX 理解”；若结果明显不符，再询问用户。 |

### 绝对禁止（违反将直接导致数据不真实）

1. 编造地点名称、地址、坐标或 POI。
2. 用直线距离、地图估算或“大概几分钟”替代路线工具返回的步行时长。
3. 把步行超时的地点列为符合条件的推荐（可以在“其他选项”里单独提示，且必须明说超时）。
4. 声称“环境安静”“不用排队”“正在营业”等无数据支撑的信息。
5. 在文件中写入或输出任何 API Key。

---

## 6. 输出前自查清单

回答前逐条确认：

- [ ] 每个地点的名称、地址都来自地点搜索返回结果
- [ ] 每个推荐都有对应的步行路线查询结果，距离与时长直接取自工具返回
- [ ] 所有推荐的步行时间都 ≤ 用户给的上限（无上限时已说明）
- [ ] 推荐数量 ≤ 用户要求且 ≤ 3
- [ ] 排序与“优先近一点”等偏好一致，且理由引用了具体数字
- [ ] 结果不足、查询失败、信息缺失都已如实说明
- [ ] 没有出现“未核实”之外的臆测描述
- [ ] 回答是表格 + 1–2 句提示，简洁可读

---

## 7. 工具能力映射

本 Skill 依赖高德 MCP Server 的两类能力；具体工具名以评测平台实际提供的为准，按能力选择：

| 能力 | 用途 | 常见工具名 |
|---|---|---|
| 地理编码 | 地名 → 坐标 | `maps_geo` |
| 周边搜索 | 按类型 + 中心点 + 半径找候选 | `maps_around_search` |
| POI 详情（可选） | 补充地址/类型 | `maps_search_detail` |
| 步行路线 | 起点 → 候选的距离与耗时 | `maps_direction_walking` |

调用时只传必要参数，避免一次拉取过多候选；对失败调用最多重试一次，仍失败则按第 5 节处理。
